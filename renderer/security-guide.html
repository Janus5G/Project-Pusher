Sikkert GitHub Ruleset uden unødig friktion

Denne opskrift beskytter main mod direkte og destruktive ændringer, men lader stadig et solo-projekt eller et lille team arbejde normalt via pull requests.

1. Klargør repository

  1. Åbn repository på GitHub.
  2. Gå til Settings → General → Pull Requests.
  3. Aktivér Allow squash merging. Du kan deaktivere merge commits og rebase merging for en enkel, lineær historik.
  4. Aktivér gerne Automatically delete head branches. Det rydder feature-branches efter merge uden at røre main.

2. Opret branch-rulesettet

  1. Gå til Settings → Rules → Rulesets.
  2. Vælg New ruleset → New branch ruleset.
  3. Navn: Protect default branch.
  4. Start med Enforcement status: Disabled, mens du udfylder og kontrollerer valgene.
  5. Under Target branches: vælg Include default branch. Brug ikke *; feature-branches skal fortsat være nemme at arbejde på.
Bypass list: Lad den helst være tom. Hvis du vil have en nødudgang, tilføj kun repository-administrator som For pull requests only. Undgå Always allow, da det igen tillader direkte, ubeskyttede ændringer.

4. Indstillinger under pull request-reglen

Hvis du arbejder alene

  • Required approvals: 0. Du kan ikke godkende din egen PR, så 1 godkendelse vil låse et solo-repository.
  • Require conversation resolution before merging: TIL.
  • Allowed merge methods: Squash.
  • Dismiss stale approvals, Code Owner review og approval of most recent push: FRA, fordi de kræver en anden person.

Hvis I er mindst to aktive udviklere

  • Required approvals: 1.
  • Require approval of the most recent reviewable push: TIL. Det beskytter mod nye ændringer efter en godkendelse uden at nulstille alle tidligere reviews.
  • Require conversation resolution before merging: TIL.
  • Allowed merge methods: Squash.
  • Require Code Owner review: kun TIL, hvis repositoryet har en vedligeholdt CODEOWNERS-fil.

5. Status checks uden at låse repositoryet

  1. Push CI-filen og lad workflowet køre mindst én gang.
  2. Redigér derefter rulesettet og aktivér Require status checks to pass.
  3. Vælg det check-navn GitHub viser fra dit workflow, typisk test. Gæt ikke navnet.
  4. Lad Require branches to be up to date before merging være FRA for et lille projekt. Det undgår gentagne CI-kørsler, hver gang main flytter sig.
  5. Ved mange samtidige pull requests: aktivér i stedet streng up-to-date-kontrol eller en merge queue.
Vigtigt: Kræv aldrig et statuscheck, som endnu ikke findes eller ikke kører på alle relevante pull requests. Ellers kan ingen merge.

6. Aktivér og test

  1. Gem rulesettet, redigér det igen, og skift Enforcement status til Active.
  2. Opret en lille test-branch, lav en ufarlig ændring, og åbn en pull request mod main.
  3. Kontrollér at direkte push til main afvises, mens PR + squash merge virker.
  4. Hvis du er låst ude: gå til rulesettet og skift midlertidigt status til Disabled; ret den konkrete regel og aktivér igen. Opret ikke en permanent bred bypass.

Rulesets kan afhænge af repositorytype og GitHub-abonnement. Hvis en anbefalet mulighed ikke vises, spring den over i stedet for at erstatte den med en bredere, mindre sikker regel.

7. Din normale arbejdsgang bagefter

  1. Opret en branch lokalt, eksempelvis git switch -c feature/kort-navn.
  2. I Project Pusher skal branch-feltet være det samme navn, eksempelvis feature/kort-navn. Push ikke direkte til main.
  3. Åbn en pull request på GitHub, vent på eventuelle checks, løs samtaler og vælg Squash and merge.
  4. Skift lokalt tilbage til main, hent den nye version, og opret næste feature-branch.

Det første push til et helt tomt repository skal ske, før rulesettet kan beskytte default-branchen.
